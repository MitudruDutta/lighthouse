# Benchmarks

Every number here comes from the running system, and every one can be run again. The measures live in the repository: `cd backend && uv run python -m app.measure <name>` runs one against the FalkorDB of `docker compose up -d` (FalkorDB 6.0.2, pinned by digest) and writes its result, with the commit it ran on, to `measurements/<name>.json`. Each writes to throwaway graphs of its own. The results below are from one laptop, in a Linux container.

## Results

| Claim | Measure | Result |
| --- | --- | --- |
| Writing needs no model | `writes`: 300 events of a live public feed, one at a time, counting model calls | 0 model calls. One write: 5.2 ms at the median, 7.8 ms at the 95th percentile. 1,168 events a second in one batch. |
| History is exact | `history`: 500 entities and 7,711 changes, written in time order | 7,711 facts read back, 0 wrong. |
| Late rows are never placed wrong | The same 7,711 changes, shuffled so that rows arrive late | 3,167 late rows `inserted` in their place. 2,271 rows came after a later row had repeated the State they fall in; each was refused as `stale` and kept as a WriteFailure. 829 read-backs differ from the source, and every one of them involves a refused row: none is wrong without a record of why. |
| Agents never double-claim | `claims`: 16 agents, each on its own connection, race for 500 tasks | 500 claims won, 0 tasks won twice. |
| Tenants are isolated | `tenants`: 200 rows in one tenant's graph, read from another's | 0 nodes, 0 search results, 0 versions seen. |
| Memory survives a restart | `restart`, then `docker compose restart falkordb`, then `restart --check` | The mark written before the restart is read after it, with FalkorDB's append-only file on. |
| Graph-wide questions are fast | 100,000 entities and 550,000 relations | First answer: 77 ms for `groups()`, 64 ms for `important()`, 233 ms for `between()` from 32 entities. Asked again: 0.2 to 0.3 ms. `connection()`: 0.5 ms for four steps. |

## A result that went against us

`memory` replays 400 days of a public dataset of daily activity counts for many places through two agents built on the library: one watches the counts, one writes lessons from what ended. Each time a place turns unusually quiet or busy, each way of guessing says whether it is back to usual within 3 days, and the guess is scored when the spell ends.

| Guess | Right | 95% interval |
| --- | --- | --- |
| Always "it passes" (no memory) | 5,141 of 5,258 (97.8%) | 97.3 to 98.1% |
| The lesson written about the place (memory) | 5,141 of 5,258 (97.8%) | 97.3 to 98.1% |
| The place's own past spells (memory) | 5,123 of 5,258 (97.4%) | 97.0 to 97.8% |

**Memory did not help on this task.** A quiet or busy place almost always recovers within three days, so a guess with no memory is already near the ceiling; the lessons said the same as the base rate every time, and the place's own past did slightly worse. It is published as measured. Showing that memory helps needs a task where a place's past changes the answer.

## Comparing with other memory stacks

There are no head-to-head numbers on this page yet, and none are borrowed from other projects' papers: a comparison is only fair on the same events, the same machine, and the same questions.

What sets the designs apart can be measured directly:

- **Model calls per write.** Memory layers that extract facts with a model, such as Mem0 and Graphiti by default, call a model on every write: latency in seconds and a cost per write. Lighthouse writes by rule, with no model: the `writes` measure above.
- **Exact answers about the past.** Versions with a start and an end let `as_of()` give what was true at any moment; the `history` measure checks every fact against its source.
- **Coordination.** Task claims and handoffs in one query each: the `claims` measure.

Published benchmarks for agent memory, such as LoCoMo and LongMemEval, ask questions about long chat histories and score a model's answers. They test conversational recall with a model in the loop, which is a different job from keeping structured events by time, and Lighthouse has not been run on them.
