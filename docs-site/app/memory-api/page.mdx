# Memory HTTP API

The Lighthouse Memory service exposes project-scoped structured memories over HTTP. Its developer console is a separate website from this documentation. The Python library connects directly to FalkorDB; it does not require a Lighthouse API key.

## Create a project key

Open the Memory console, create a project, then choose **API keys → Create API key**. Name the key, select read and/or write access, and choose its expiry. Copy the secret once and keep it in your application server’s environment. The console lists only a prefix after creation. Revoke unused keys from the same page.

A key selects exactly one project graph. Clients cannot change the project using a request parameter. Account sessions and project keys are different credentials: sessions access your console; keys access the `/v1` memory endpoints.

## Store a memory

Use your service address as `LIGHTHOUSE_MEMORY_URL` and your key as `LIGHTHOUSE_MEMORY_KEY`. This example is a request format; no request is sent by this page.

```bash
curl "$LIGHTHOUSE_MEMORY_URL/v1/memories" \
  -H "Authorization: Bearer $LIGHTHOUSE_MEMORY_KEY" \
  -H "Content-Type: application/json" \
  -d '{"key":"decision-001","title":"Preferred language","text":"Use Python examples.","metadata":{"source":"user preference"},"links":[]}'
```

Reusing an identifier writes a new version when its values change. Writes use UTC whole-second observation times. Conflicting updates to one identifier within the same second are refused; retry after the clock advances. Earlier versions remain available through history. `links` contains identifiers already stored in the same project and replaces that memory’s current outgoing connections.

## Read and follow connections

| Method | Endpoint                                          | Scope          | Result                                                  |
| ------ | ------------------------------------------------- | -------------- | ------------------------------------------------------- |
| POST   | `/v1/memories`                                    | `memory:write` | Write receipt: created, changed, unchanged, or inserted |
| GET    | `/v1/memories?q=python`                           | `memory:read`  | Up to 100 memories; optional full-text search           |
| GET    | `/v1/memories/decision-001/history`               | `memory:read`  | Stored versions in `data`                               |
| GET    | `/v1/connections?start=note-002&end=decision-001` | `memory:read`  | Connection paths, bounded to six hops, in `data`        |

List responses include `data` and `limit`. No pagination is currently available. The console’s usage page records successful memory operations; it is an activity record, not a billing meter. Failed and refused requests are not included in those totals.

## Coordinate agents

A project key also acts as one agent, named by the key: create one key per agent, such as `watcher` or `reviewer`. The key decides who wrote an entry, who holds a task, and who gives or accepts a handoff. A request cannot name another writer.

An episode records one event in order. Start it about memories that exist, append entries that cite their evidence, and close it with an outcome:

```bash
curl "$LIGHTHOUSE_MEMORY_URL/v1/episodes/overload-1/entries"   -H "Authorization: Bearer $LIGHTHOUSE_MEMORY_KEY"   -H "Content-Type: application/json"   -d '{"type":"observation","values":{"expected":5},"cites":{"memories":["pump-2"],"entries":[],"episodes":[]}}'
```

| Method | Endpoint                               | Scope          | Result                                                                 |
| ------ | -------------------------------------- | -------------- | ---------------------------------------------------------------------- |
| POST   | `/v1/episodes`                         | `memory:write` | `{"id","about":[memory ids]}` starts an episode: opened or exists      |
| POST   | `/v1/episodes/overload-1/entries`      | `memory:write` | Appends an entry; the receipt names it `overload-1/1`, `overload-1/2`… |
| POST   | `/v1/episodes/overload-1/close`        | `memory:write` | Records `{"outcome":{…}}` as the last entry; the episode takes no more |
| GET    | `/v1/episodes/overload-1`              | `memory:read`  | The episode with its entries in order, each with what it cites         |
| GET    | `/v1/memories/pump-2/episodes`         | `memory:read`  | Episodes about one memory, newest first, each with its outcome         |
| POST   | `/v1/tasks`                            | `memory:write` | `{"id","kind","about","after":[task ids]}` adds an open task           |
| POST   | `/v1/tasks/claim`                      | `memory:write` | `{"kind","lease"}` gives this agent the oldest free task, or `null`    |
| POST   | `/v1/tasks/review-1/complete`          | `memory:write` | Marks the task done; only the agent that holds it can                  |
| POST   | `/v1/tasks/review-1/release`           | `memory:write` | Opens the task again for another agent                                 |
| POST   | `/v1/handoffs`                         | `memory:write` | `{"id","to","points_to":{…},"values":{…}}` passes work to an agent     |
| GET    | `/v1/handoffs?waiting=true`            | `memory:read`  | Handoffs given to this agent, oldest first; `false` includes accepted  |
| POST   | `/v1/handoffs/h1/accept`               | `memory:write` | Accepts a handoff given to this agent, once                            |

`cites` and `points_to` name entry ids, episode ids, and memory ids, each of which must exist in the project. A claim is one atomic step, so two agents never hold the same task. A task with `after` waits until those tasks are done. A claim with a `lease` in seconds, up to seven days, can be taken by another agent once it runs out.

## Limits and errors

Requests are bounded to 64 KiB. Identifiers contain 1–100 characters: letters, digits, `_`, `.`, `:`, `/`, or `-`, starting with a letter or digit. Titles support 200 characters, memory text 12,000 characters, metadata 12,000 JSON characters, and each memory up to 50 outgoing connections.

Episode, task, and handoff ids follow the same rule without `/`, because an entry id is the episode id, `/`, and its number.

Each project key permits 120 authenticated requests per UTC minute. Invalid credentials return `401`; insufficient scope, or a handoff given to another agent, returns `403`; an unknown episode or handoff returns `404`; a closed episode, or a task this agent does not hold, returns `409`; invalid input or a reference that does not exist returns `422`; excessive request size returns `413`; request limits return `429`. Service failures return a safe `503` message, with diagnostic details kept in server logs.

The same operations are MCP tools at `/mcp`, for Claude Code, Claude Desktop, and your own agents: see [agents, MCP, and plugins](/mcp).

The HTTP service covers structured writes, text search, history, connection paths, episodes, tasks, and handoffs. Lessons, playbooks, promotion, conversations, and semantic recall are available through the [Python library](/reference), not these HTTP endpoints.

## Preview status

The current service is a developer preview, free while billing is not active. Managed hosting plans, email verification, password recovery, and team invitations are not active yet. An account has up to 5 workspaces, each with up to 20 projects; each project has a separate graph and up to 20 active keys, with expiry between 1 and 365 days.

A project or a workspace can be deleted from the console's settings, after typing its name. Deleting a project deletes its graph, with every memory and version, its keys, and its usage; deleting a workspace deletes its projects. An account's only workspace cannot be deleted.
